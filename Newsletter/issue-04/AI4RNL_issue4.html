The Big Number
100
attempts to reproduce one published table,
with differences still left at the end

Kubota and coauthors gave an AI system a paper, its data, and a codebook. The system wrote and ran analysis code, compared its output with the published result, and revised the code. For one table, it used all 100 attempts. Its best score was 74 out of 100. Coefficient signs mostly aligned, but sample sizes, magnitudes, and significance levels still differed. The useful output was the discrepancy report: it showed where documentation, variable coding, or the generated code needed a closer look.

Source: Kubota et al., LLM-Assisted Replication for Quantitative Social Science (2026)  ·  code and outputs

Reviewing Code and Results

Catch reproducibility problems before submission

The gaps in the example above are common reasons reproducibility checks fail: unclear variable construction, undocumented missing-value rules, changing samples, and differences between the written method and the code. Many of these problems can be caught during project work, before the package reaches a reviewer.

1.  Regular code review can catch risky merge logic, undocumented sample restrictions, hardcoded paths, missing seeds, and outputs edited by hand.
2.  Good project practices make that review easier: one main script, project-relative paths, documented inputs, clear intermediate files, and tables and figures generated by code.
3.  Coding agents can help apply these checks across a project. They can inventory files, compare the README with the code, trace outputs, and flag places that need review. Each finding should include evidence that a researcher can check.
4.  At Impact Analytics, we developed the Reproducibility Package skill. It is built on our extensive experience reviewing reproducibility packages and guides a coding agent through four phases: Audit, Outline, Build, and Run check.
5.  It can audit an existing package or help reorganize a legacy project. It pauses between phases so you can review the findings and approve changes. The slides give a short walkthrough.

Materials: setup guide  ·  slides  ·  latest skill release  ·  demo project

Try This Today  ·  10 minutes

Run the reproducibility skill’s Audit phase on one project. Stop before it proposes or makes changes.

1. Open VS Code and confirm that GitHub Copilot or Claude Code responds in the chat panel. The setup guide covers both options.
2. Download the latest skill release. Unzip it and place the full reproducibility-skill/ folder under .agents/skills/ in the project root.
3. Open your project in VS Code. If you prefer to practice first, download the optional demo project and leave its folders unchanged.
4. Ask your coding agent:

Use the reproducibility skill to audit this project. Complete the Audit phase only. Report each finding with the file, evidence, and requirement it relates to. Do not change files.

Pick one finding and verify it yourself in the cited file. Mark it confirmed, unclear, or a false positive. When the agent asks to continue, stop there.

Have more than 10 minutes? Read the full audit and sort findings into three groups: package structure, code and paths, and documentation. Approve an Outline only after you agree with the proposed fixes.
