The Big Number
1 in 5
PRWP reproducibility packages that pass verification
on the first try — most need another round (or two).

When the Reproducible Research team checks a Policy Research Working Paper package, they ask a simple question: can an outsider run the code and get the paper’s tables and figures exactly? Only about one in five packages clear that bar on first review; the average package goes through more than two revision rounds. That gap is not usually “bad research” — it is missing files, hardcoded paths, hand-edited tables, undocumented data, and other fixable package problems. Our reproducibility coding skill is designed to help you and your coding agents catch those failure patterns before you submit.

Source: World Bank Impact Evaluations blog — 500 packages on RRR (published figure; confirm current rate with the reproducibility team before quoting as up-to-date)

In Case You Missed It

AI Skills to Facilitate Reproducible Research

Quick recap of the July 16 session (RG: July 23). The short version: there is a ready-made AI skill that walks you through turning an existing project folder into a package the reproducibility team can actually verify.

1.  Start from a project you already have — even a messy one. The goal is a package that runs on someone else’s computer and regenerates the paper’s tables and figures, following the reproducibility standard.
2.  With the skill, there’s no need to paste the whole standard into a chat. Install the World Bank Reproducibility Package skill: it includes the official checklist, README templates, and a list of the 14 most common reasons packages fail verification (hardcoded Dropbox paths, no main script, missing seeds, hand-edited tables, mystery data files, and so on).
3.  Work in four steps, with a pause after each: Audit (what’s wrong?) → Outline (what should we change?) → Build (make the fixes) → Run check (does it actually regenerate every exhibit?). Nothing is rewritten until you approve the plan.
4.  The first step is read-only: the skill inventories your files and reports every checklist gap and failure pattern it finds — then it stops and waits for you.
5.  Looking clean on paper is not enough. The last step re-runs the package from scratch — or gives you a checklist to run it yourself, according to your instructions — so every table and figure is produced by the code, not copied in by hand.

Materials: session page  ·  slides  ·  skill repo  ·  questions: reproducibility@worldbank.org

Try This Today  ·  10 minutes

Drop the skill into one existing project and run Phase 1 (Audit) only. Do not approve Outline or Build yet.

1. Download the skill: repo or zip.
2. At the project root: create .agents/skills/ and copy reproducibility-skill/ into it.
3. In your AI coding agent of choice, type:

Prepare a reproducibility package for this project.

Read the audit report: checklist gaps and the common failure patterns (paths, missing main script, hand-made outputs, undocumented data). When it asks to proceed to Outline, say not yet — the audit alone is the 10-minute win.

Have more than 10 minutes? Practice on the session demo project (intentional hardcoded paths, mystery merged data, hand-formatted table). Use git so you can see every change the agent proposes.

Field Notes  ·  beyond the trainings

Outside the Bank: precise reproducibility is still hard

The SCORE project in Nature tried to reproduce published claims across the social and behavioural sciences. Even among papers where data could be obtained, only about half were rated precisely reproducible. Where authors had shared both data and code, the rate jumped; where analysts had to rebuild the dataset from public sources, it collapsed.

That is a different problem from asking an AI to invent analysis from a PDF — and closer to what we do: turn a real project folder into a package someone else can run. Field Notes walks through SCORE’s numbers and what they imply for packaging, sharing, and verification.
