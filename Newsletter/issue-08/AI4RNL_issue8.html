The Big Number
95.5% → 89.0%
GPT-4’s score on a maths benchmark,
before and after reviewing its own answers

Ask a model to answer, then ask it to check its answer and fix any mistakes. In 2023 several papers reported that this made models better. Huang and coauthors looked closer and found that those papers had, one way or another, told the model when it was wrong. Take that away, so the model has to judge its own work unaided, and the gains vanish. GPT-4 scored 95.5% on grade-school maths problems at the first attempt. After one round of self-review it scored 91.5%. After two, 89.0%. It changed right answers to wrong ones more often than the reverse.

The lesson for code is plain. The agent that wrote your cleaning script is the worst-placed reader of it, for the same reason you are the worst-placed reader of your own do-file. Impact Analytics’ November 9 training on AI code review was about a second reader with a checklist. This issue is about making that a habit.

Source: Huang et al., “Large Language Models Cannot Self-Correct Reasoning Yet”, ICLR 2024. The task is reasoning, not code; Field Notes covers the code-review studies.

In Case You Missed It

AI Skills for Code Review

A quick recap of Impact Analytics’ November 9 training on AI skills for code review, a repeat of a session from the October AI-Enabled Research Bootcamp, for everyone who missed it. DEC used to pair people up for peer code review against a checklist. The skill turns that checklist into something you can run on your own code, at any stage, without waiting for a colleague.

1.  Your name is on code you didn’t write. RAs and consultants write most of it, and now agents write more of it, faster. The TTL signs the paper. Reading every line by hand is not feasible. Not reading it is not acceptable either.
2.  Research code fails quietly. A merge that doubles rows. Duplicates dropped by whichever came first. A random draw with no seed. A −99 that enters a mean. A path that only works on one laptop. None of these crash. The number changes. And a package that reproduces perfectly can still be wrong: our reproducibility check asks whether it runs, not whether the merge kept the right rows.
3.  The checklist is the point. “Review my code” gets a different review every time, at a different depth. The skill carries sixty-odd flags from DEC’s peer review checklists and the reproducibility team’s failure list, each with a severity set by consequence, from Critical to Low. Same checks every time, so reviews can be compared across projects and people.
4.  Two phases, with you in the middle. Before it lists a single file, the agent asks you to confirm there is no confidential or identifying data in the folder (“probably fine” counts as no). Phase 1 reads code and documentation only: no running, no opening data, no edits. You get a table: flag, severity, file and line, and whether the agent can fix it. Phase 2 happens only on a Git branch, and only for what you approve.
5.  Three kinds of finding. Yes: the fix is clear, approve it. Conditional: it needs a value first, like the seed. No: a research decision only you can make, like which observations to drop, so you decide, document, and then ask the agent to implement your choice. “Do the straightforward ones” means the Yes rows. defer leaves an item open without changing anything.

Try This Today  ·  10 minutes

Run the read-only review on one script you finished this month. Don’t let it change anything yet.

1. Install the skill. Download research-code-review.zip, unzip it, and put the whole research-code-review/ folder under .agents/skills/ at the project root. The whole folder, not just SKILL.md; the checklist lives next to it.

2. Clear the folder of data. Move any data files out, or practise on the demo project, where everything is synthetic.

3. Open a new session and ask for a selected-files review:
Read .agents/skills/research-code-review/SKILL.md and review only:
- code/<your script>
Treat this as a selected-files review.
Answer the privacy question honestly. A hedge counts as no, and the agent will offer a code-only review instead.

4. Read the High and Critical rows against the code. Open the file at the line it cites. Real, unclear, or a false alarm? Then pick one Conditional row and answer it (STAB-001: provide: seed = 20261118). Reply defer to the rest. When it offers Phase 2, stop there.

Have more than 10 minutes? Let it implement the one item you approved, on a new Git branch, and read the diff line by line. Then open another fresh session and run the review again on the changed file. If the second review is short, the fix held. The Deep Dive is about making that loop a habit.

Field Notes  ·  beyond the trainings

The second reader

The Big Number is what self-review does. Field Notes is about the evidence for the alternative, and the parts of it that should make you careful.

A separate AI critic’s review of ChatGPT’s code was preferred over an experienced human’s 63% of the time, and a human working with the critic did better still. The critic also invented problems more often. In a year-long deployment at a software firm, developers acted on three in four AI review comments, and pull requests took two hours longer to close. Field Notes puts the three studies together and says what they mean for Stata and R.
