The Big Number
95.5% → 89.0%
GPT-4’s score on a math benchmark,
before and after reviewing its own answers

AI models are bad at correcting their own mistakes. Huang and coauthors asked GPT-4 a set of grade-school math problems, then asked it to review its own answers and fix any errors, with no hint about which ones were wrong. It scored 95.5% at the first attempt, 91.5% after one round of self-review, and 89.0% after two. It changed right answers to wrong ones more often than the reverse. Earlier studies that found self-review helpful had, one way or another, told the model when it was wrong.

The lesson for code is plain. The agent that wrote your cleaning script is the worst-placed reader of it, for the same reason you are the worst-placed reader of your own do-file. As agents write more of our research code, someone else has to read it. Impact Analytics’ November 9 training on AI code review was about a second reader with a checklist. This issue is about making that a habit.

Source: Huang et al., “Large Language Models Cannot Self-Correct Reasoning Yet”, ICLR 2024. The task is reasoning, not code; Field Notes covers the code-review studies.

In Case You Missed It

AI Skills for Code Review

A quick recap of Impact Analytics’ November 9 training on AI skills for code review (slides here). DECDI used to pair people up each quarter to review each other’s code against a checklist. It was useful, but time and coordination limited who could take part. The skill turns those checklists into a review you can run on your own code whenever it is ready. Ankriti Singh, María Reyes Retana and Maria Jones tell the full story on the Development Impact blog: AI is writing more research code: who is reviewing it?

1.  You sign off on code you didn’t write. Research assistants and consultants write much of a project’s code, and AI agents now write more of it, faster. The paper still carries your name, so you need to know the code is right, and reading every line by hand is rarely feasible. Code behind Policy Research Working Papers is also expected to be public in the Reproducible Research Repository, which is one more reason to clean it up first. An agent can help with the reading.
2.  Research code fails quietly. There is a difference between code that runs and code that is accurate and error-free. A merge that doubles rows. Duplicates dropped by whichever came first. A random draw with no seed. A −99 that enters a mean. A path that only works on one laptop. None of these crash. The number changes. And a package that reproduces perfectly can still be wrong: in one recent audit, 26 of 110 published papers had substantive coding errors, even though 85% of them reproduced.
3.  A skill gives the same review every time. Ask an agent to “review my code” and you get different checks at a different depth on each run. The skill carries more than 60 checks from DECDI’s peer review checklists and from the failures the reproducibility team sees most. Each finding gets a severity based on what it could do to your results, from Critical to Low, not on how hard it is to fix.
4.  It keeps your data out of the review. Before it lists a single file, the agent asks you to confirm that the folder holds no confidential or identifying data. Then it reads code and documentation only. It does not open data, run scripts or edit files.
5.  Feedback first, changes only on your say. The review ends with a report, not with edits. Each finding says whether the agent could fix it: Yes (a mechanical fix), Conditional (it needs a value from you, like the seed) or No (a research decision, like which observations to drop). You choose what gets fixed. The agent makes those changes on a Git branch so you can read every line and undo any of it. Analytical choices stay with you.

Try This Today  ·  10 minutes

Run the read-only review on one script you finished this month. Don’t let it change anything yet.

1. Install the skill. Download research-code-review.zip, unzip it, and put the whole research-code-review/ folder under .agents/skills/ at the project root. The whole folder, not just SKILL.md; the checklist lives next to it.

2. Clear the folder of non-public data. Move any confidential or identifying data out of the project folder, unless you are running the review with Claude Enterprise, which is approved for it. Or practice on the demo project, where everything is synthetic.

3. Open a new session and ask for a selected-files review:
Read .agents/skills/research-code-review/SKILL.md and review only:
- code/<your script>
Treat this as a selected-files review.
Answer the privacy question honestly. A hedge counts as no, and the agent will offer a code-only review instead.

4. Read the High and Critical rows against the code. Open the file at the line it cites. Real, unclear, or a false alarm? Then pick one Conditional row and answer it (STAB-001: provide: seed = 20261118). Reply defer to the rest. When it offers Phase 2, stop there.

Have more than 10 minutes? Let it implement the one item you approved, on a new Git branch, and read the diff line by line. Then open another fresh session and run the review again on the changed file. If the second review is short, the fix held. The Deep Dive is about making that loop a habit.

Field Notes  ·  beyond the trainings

The second reader

The Big Number is what self-review does. Field Notes is about the evidence for the alternative, and the parts of it that should make you careful.

A separate AI critic’s review of ChatGPT’s code was preferred over an experienced human’s 63% of the time, and a human working with the critic did better still. The critic also invented problems more often. In a year-long deployment at a software firm, developers acted on three in four AI review comments, and pull requests took two hours longer to close. Field Notes puts the three studies together and says what they mean for Stata and R.
